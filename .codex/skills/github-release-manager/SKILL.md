# GitHub Release Manager

사용자가 제공한 Release 워크플로 방식으로 저장소의 릴리스를 관리한다. 설명과 릴리스 노트는 기본적으로 한국어로 작성하되 기존 저장소의 언어 관례를 존중한다.

## 작업 범위

- 워크플로 구축 요청이면 설정·스크립트·노트를 구현하고 검증한다. 스킬 작성이나 워크플로 준비 요청만으로 push, 태그 생성, 실제 게시까지 수행하지 않는다.
- 실제 릴리스 요청이면 이미 허용된 범위에서 준비부터 CI 결과와 게시 결과 확인까지 진행한다. 승인된 작업을 반복 확인하지 않는다.
- 기존 `AGENTS.md`, 릴리스 설정, 버전 규칙, 사용자 변경 사항을 먼저 확인한다. 이슈·PR 절차는 해당 저장소 규칙이나 사용자 요청에 있을 때 따른다.

## 저장소에 맞추기

먼저 앱 루트, 패키지 매니저와 lockfile, 버전 원본, stamp 스크립트, 빌드 명령, 출력 경로, 대상 OS·아키텍처, 서명 설정, 업데이트 구현을 확인한다.

사용자 예시의 기본값은 다음과 같다. 기존 프로젝트의 동등한 설정에 매핑하고 이름을 기계적으로 덮어쓰지 않는다.

| 항목 | 예시 기본값 |
| --- | --- |
| 트리거 | `main`, `master` push |
| 버전 원본 | `src/main/appVersion.ts`의 `APP_VERSION` |
| 표시 버전 | `YYYY.MM.DD.HH.mm` |
| 태그 / 제목 | `v<버전>` / `<버전>` |
| Node / 설치 | Node 22 / `npm ci` |
| 버전 반영 | `npm run version:stamp -- <버전>` |
| OS 빌드 | `npm run build:win`, `npm run build:mac` |
| 환경변수 | `A8A_APP_VERSION`, `A8A_UPDATE_GITHUB_REPO` |
| 노트 | `build/release-notes.md` |

날짜 버전을 새로 정할 때 저장소의 시간대를 사용한다. 관례가 없으면 사용자 환경의 시간대를 명시하고, 같은 분의 태그 충돌을 확인한다. 이 5개 숫자 형식은 SemVer로 간주하지 않는다. 패키징 도구가 요구하는 내부 버전과 표시 버전의 기존 변환을 유지하거나 명시적으로 구현한다.

## 구현 흐름

워크플로를 만들거나 수정할 때 [references/release-workflow.md](references/release-workflow.md)를 읽고 다음 의존관계를 유지한다.

1. `version`: 버전 원본을 한 번 읽고 검증하여 job output으로 제공한다.
2. `windows-build`, `macos-build`: `version`에 의존하며 각 OS에서 의존성 설치 → 버전 반영 → 패키징 → 필수 산출물 검증 → 체크섬 생성 → artifact 업로드를 수행한다.
3. `publish-release`: 위 세 job이 성공한 뒤 해당 실행의 artifact만 내려받아 검증하고 GitHub Release를 게시한다.

버전 원본과 릴리스 노트를 함께 갱신한다. 노트는 직전 릴리스 이후 실제 변경 사항에 근거해 사용자에게 영향을 주는 기능·수정·주의사항을 기록한다. 구현되지 않은 변경이나 확인하지 않은 테스트 결과를 쓰지 않는다.

기존 버전·태그가 있으면 정상적인 신규 배포는 새 버전을 사용한다. 재실행 복구에서는 기존 태그의 커밋과 게시된 파일을 먼저 확인한다. 태그 이동, 릴리스 삭제, `--clobber` 덮어쓰기를 자동 복구 기본값으로 삼지 않는다. 상태 충돌이나 불명확한 게시 실패가 있으면 추가 게시를 멈추고 원인을 보고한다.

## 검증과 완료

- 설치된 `actionlint`가 있으면 사용하고, 없으면 YAML 구문·job 의존성·output 참조·셸·파일 경로를 검토한다. YAML 파싱만으로 Actions 실행 검증이 끝났다고 하지 않는다.
- 저장소에 맞는 버전 추출·stamp 검증과 관련 빌드 검사를 실행한다. 다른 OS의 빌드를 로컬에서 검증했다고 주장하지 않는다.
- `if-no-files-found: error`에만 의존하지 말고 각 필수 산출물의 존재를 확인한다. 다운로드한 파일 기준으로 SHA256을 재검증한다.
- 실제 게시 요청에서는 해당 커밋의 Actions 실행과 릴리스의 태그·제목·노트·asset 목록을 확인한다. 실패하면 실패 job과 원인을 구분하고, 수정 없이 같은 게시 명령을 반복하지 않는다.
- 완료 보고에는 변경 파일, 버전·태그, 수행한 검증과 미실행 검증, 실제 게시했다면 Actions·Release URL을 간결하게 적는다.
